What this demo shows

    
A cross-domain AI agent remediation scenario where Sarah (an engineer at Org A) asks
    OpenCode (her Org A AI agent) to fix a CVE found in a repo owned by Org B.
    Because Org B has its own IdP and access control, OpenCode cannot act directly — it must
    assert Sarah's delegation cross-domain using the ID-JAG protocol.


    
Two signed objects, and they are not the same thing.
    A credential (typ=JOSE, type AgentBadge) is signed with the
    org's Vault trust-authority key and published to the Identity Node, where anyone can resolve it
    at /v1alpha1/vc/{id}/.well-known/vcs.json. It says what an agent is and what it
    may do or delegate, and lasts about an hour. An assertion
    (typ=oauth-id-jag+jwt) is minted by Keycloak per task, lives about five minutes, and
    says this particular request is authorised. Policy at the four Envoy boundaries acts on the
    assertion; the credential is what a counterparty resolves independently before
    trusting a handoff. Where a step says "sub-badge" it means an assertion — the JWT header type is
    always authoritative.


    
Conventional identity systems assume the caller is the human principal; an autonomous agent
    acting under delegated authority breaks that assumption. This is a reference implementation of
    the alternative, built on three design principles:

    

      
PrincipleWhat it means here

      
Identity ≠ ExecutionWho initiated (Sarah's sub) and who
        executed (the agent's act) are kept distinct at every hop — never collapsed
        into one identity, so human accountability survives every delegation.

      
Independent Trust DomainsOrg A and Org B each verify signatures
        against their own JWKS and evaluate their own policy — no shared IdP, PKI, or governance
        is required for either side to trust the other's assertions.

      
Complete AuditabilityEvery cross-domain action produces a verifiable
        record — actor, delegator, capability, resource, policy decision, outcome — carried in the
        token's act chain itself, not a log that could be edited after the fact.

Step-by-step walkthrough


    
Phase A — OpenCode authenticates & registers its own identity (steps 1–3)

    
Sarah signs in via OIDC password grant using the opencode-agent client in Org A's Keycloak realm.
    OpenCode does not start working yet — it first registers its own CIMD identity
    (AGNTCY-opencode-agent) at identity-node, the same Vault-backed proof-JWT flow described
    below, then resolves it back to confirm the registration.


    
Policy-scoped badge — least privilege before any work runs (steps 4–5)

    
OpenCode presents Sarah's delegated access token, plus the action and repo it wants to perform,
    to Envoy A + inline OPA at a new endpoint: /api/badge-scope-check. Policy decides
    whether — and how narrowly — to scope this task, returning a scoped-down intent
    (e.g. scan-remediate:demo-admin/payments-service) as a response header. Only then
    does OpenCode issue the badge, bound to exactly that intent — it cannot be broader than what
    policy already approved. The badge is a genuine W3C Verifiable Credential: built by the agent,
    signed with org-a's Vault trust-authority key (the same key CIMD proofs use — the private
    half never leaves Vault), and published to the AGNTCY Identity Node, which verifies it and
    serves it at /v1alpha1/vc/{id}/.well-known/vcs.json. Note the node's API is
    publish/verify/revoke/search with no issue: it registers credentials the issuer has already
    signed, so the trust anchor is the org's registered issuer key rather than any one service's
    keypair.

    
POST /api/badge-scope-check          # Envoy A + inline OPA
  Authorization: Bearer <Sarah's access token>
  x-agntcy-requested-action: scan-remediate
  x-agntcy-requested-repo: demo-admin/payments-service
→ 200 OK
  x-agntcy-scoped-intent: scan-remediate:demo-admin/payments-service

POST /v1alpha1/vc/publish             # AGNTCY Identity Node
{"vc":    {"envelopeType": "CREDENTIAL_ENVELOPE_TYPE_JOSE", "value": "<JOSE VC>"},
 "proof": {"type": "JWT", "proofValue": "<Vault-signed proof JWT>"}}
→ 200

POST /v1alpha1/vc/verify              # the node verifies, not the issuer
→ {"status": true, "document": {"type": ["VerifiableCredential", "AgentBadge"], …}}


    
The work — scan + a real OpenCode agent (steps 6–6b)

    
Only now, under the task-scoped badge, does the actual work begin: a mocked CVE scan, then a
    real remediation analysis from the real open-source OpenCode agent (opencode.ai, headless
    in its own opencode-server container) — a genuine LLM call, not a canned response.
    This step is deliberately non-fatal: without a reachable model provider it reports
    skipped and the identity chain continues, so the security-relevant part of this demo
    never depends on model availability.


    
AGNTCY Directory — per-turn record & agent discovery (steps 7–8)

    
OpenCode pushes an OASF record to the AGNTCY Directory Node (dir-apiserver:8888, gRPC).
    The directory returns a CID — a content-addressed, immutable identifier that proves this remediation turn happened.
    OpenCode then searches the directory by agent name to discover the triage-agent's endpoint.

    
# Push turn record (gRPC bidirectional stream)
stub.Push([Record(data={
    "name": "opencode-agent", "schema_version": "1.1.0",
    "annotations": {"cve": "CVE-2024-12345", "repo": "…"}
})])
→ RecordRef(cid="baeare…")   # immutable, content-addressed

# Discover triage-agent
stub.SearchRecords(SearchRecordsRequest(queries=[RecordQuery(
    type=RECORD_QUERY_TYPE_NAME, value="triage-agent"
)]))
→ [SearchRecordsResponse(record=...)]


    
CIMD note: identity-node's actual REST API has no "register app / issue
    badge" concept — it needs a self-issued proof JWT to mint or resolve an id. At startup,
    identity-node-init registers org-a as a local trust authority: it creates an
    RSA-2048 key in Vault's transit engine (the private key never leaves Vault), reads back the
    public key, and self-signs a proof JWT (iss=agntcy:org-a, a sub_jwk claim
    carrying the public key) via Vault's /transit/sign API to register the issuer. Steps
    2–3 above sign a fresh proof JWT the same way to mint and resolve an id for
    opencode-agent itself under org-a's authority.


    
Cross-domain token exchange (steps 9–12)

    
OpenCode mints an ID-JAG assertion at Keycloak A itself — a real
    grant_type=token-exchange call handled by a custom SPI
    extension (keycloak-idjag-spi), following
    draft-ietf-oauth-identity-assertion-authz-grant's
    requested_token_type=urn:ietf:params:oauth:token-type:id-jag.
    The result is a short-lived RS256 JWT with sub=sarah@org-a.example,
    act_chain=[opencode-agent], aud=KC-B org-b realm,
    scope=triage:create, and intent=[create-pr-fix] —
    signed with Keycloak's own realm key, not a separate mock issuer's
    throwaway keypair. Before it ever leaves Org A, Envoy A + inline OPA independently re-check its
    scope, intent, and delegation-chain depth (the egress PDP). Org B's Keycloak then validates the
    assertion against that same JWKS, maps Sarah's identity, and issues a scoped access
    token. Triage's later narrowed sub-badge is minted the same native way, by
    Keycloak B through its own copy of the SPI — no mock issuer remains
    anywhere in the delegation path.

    
POST /realms/org-a/protocol/openid-connect/token   # Keycloak A
  grant_type          = urn:ietf:params:oauth:grant-type:token-exchange
  subject_token       = <Sarah's exchanged KC-A access token>
  subject_token_type  = urn:ietf:params:oauth:token-type:access_token
  requested_token_type = urn:ietf:params:oauth:token-type:id-jag
  audience            = http://keycloak-b:8080/realms/org-b
  scope               = openid triage:create
  target_client_id    = triage-agent
  act_chain           = opencode-agent
  intent              = create-pr-fix
→ {"access_token": "eyJ…", "issued_token_type": "urn:ietf:params:oauth:token-type:id-jag"}

POST /realms/org-b/protocol/openid-connect/token
  grant_type = urn:ietf:params:oauth:grant-type:jwt-bearer
  assertion  = eyJ…
  client_id  = triage-agent
  scope      = triage:create
→ {"access_token": "eyJ…", "scope": "triage:create"}


    
Org B — Triage agent & bounded sub-agent (steps 13+)

    
OpenCode calls POST /api/ticket through Envoy with the scoped
    access token and signed actor token. Envoy validates both signatures and
    runs the inline OPA delegation policy — and then Triage repeats, inside Org B,
    exactly the lifecycle OpenCode just ran in Org A:

    
    
      
  1. Verify what it was handed. Triage fetches Keycloak A's JWKS and
      re-verifies the ID-JAG's signature, issuer, audience, and act-chain
      in-agent — independently of the gateway that already checked it.
    2. 
      
  2. Register its own identity. It mints and resolves its own CIMD id
      (AGNTCY-triage-agent) at identity-node, proven with a JWT signed by
      org-b's Vault key. Org B is a separate registered trust authority: two orgs,
      two independent signing keys, one shared identity node.
    3. 
      
  3. Ask policy how far it may narrow. Before any sub-badge exists, Triage
      calls /api/subbadge-scope-check on Envoy B + inline OPA, which
      returns the approved scope and the exact resource — the narrowing is policy's
      decision, not the agent's.
    4. 
      
  4. Work — create the ticket, plan the remediation, pick the sub-agent.
    5. 
      
  5. Delegate narrower. Keycloak B natively mints the sub-badge
      (same keycloak-idjag-spi extension, signed with org-b's realm key):
      caps ⊆ parent — only gitea:write gitea:pr, no triage:create —
      with the act-chain Sarah → OpenCode → Triage, signed intent
      create-pr-fix, and signed resource demo-admin/payments-service.
      Triage also pushes its own turn record to the Directory.
    6. 
    

    
Triage then looks Sub-Agent up in the Directory by name — delegates are discovered,
    not hardcoded — and spawns it with the narrowed badge.


    
The leaf of the chain — Sub-Agent's own lifecycle

    
Sub-Agent runs the same shape a third time, one level down:

    
    
      
  1. Verify before redeeming. It checks the sub-badge against Keycloak B's
      JWKS before presenting it: really an ID-JAG (typ=oauth-id-jag+jwt),
      addressed to this agent (client_id=sub-agent), act-chain matching the spawn,
      bound to this repository, and — the point of the whole exercise — granting nothing beyond
      gitea:write gitea:pr. A badge that fails any check never reaches Keycloak B.
    2. 
      
  2. Register its own identity (AGNTCY-sub-agent) under the org-b trust
      authority. Every agent in the demo, in both orgs, now holds a real cryptographic identity.
    3. 
      
  3. Work under the credential. It redeems the badge for a local access token, then
      sends both that token and the original sub-badge through Envoy's resource listener. Inline
      OPA permits only the repo-bound push and pull-request operations before Gitea Gateway can
      use its admin credential — and refuses the same PR against the deny-listed
      demo-protected repo, even though the token still carries gitea:pr.
    4. 
      
  4. Record the turn in the Directory. Three turn records now exist — OpenCode's,
      Triage's, and Sub-Agent's — so the whole delegation is reconstructible from the Directory
      alone, independently of the tokens.
    5. 
    

    
Sub-Agent delegates to nobody, so there is no narrowing for policy to approve and no
    sub-badge for it to mint: the chain ends here, which is exactly what "bounded" means.

Keycloak 26.7 feature flags required:
    --features=identity-assertion-jwt,token-exchange-delegation,parameterized-scopes

    These enable the ID-JAG receiver (jwt-bearer grant), RFC 8693 delegation scope, and parameterized scopes for narrow tokens.
